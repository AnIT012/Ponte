v0.2 と、その後の追補を1つにまとめたものです。内容（ルールと書き方）は v0.2 から変えていません。 0〜2章、5章の主なパーツ、6章の「画面の小さな部品」、11〜12章、14章は確定しています。

0. コンセプト

Ponte は、プログラムのいちばん上の層に書く言語です。

  • 書くのは、何が欲しいか、何をしてはいけないか、何がまだ決まっていないかです。どうやるかは書きません。
  • Python や Java などの今までの言語は、Ponte の下で動く層になります。今の高級言語にとってのアセンブリと同じ位置です。
  • 書いたことは必ず守られる約束です。決めていないことが残っていれば動かず、書いていない操作はできず、例に合わないものは通りません。
  • 自分だけで書いても完結します。中身も Ponte の do で書けます。AI と作るときは、同じ仕様が AI への指示であり、AI が守る約束になります。
  • if、for、true/false はありません。これらは「どうやるか」を書くための道具だからです。

目標は次の3つです。

  • 覚える言葉を少なくし、読めばわかる言語にします。
  • 9割は言語の中で書けるようにします。データとルールがあるもの（アプリ、API、定期処理、業務の流れ）は、この言語だけで作れます。
  • 残りの1割は action の中身に閉じ込めます。約束（example、never、else）を先に書き、中身は自分で書くか、下の層の言語で書くか、AI に任せます。どれを選んでも、同じ約束で確かめます。

1. 設計原則

  1. パーツは少なくし、1つのパーツには1つの仕事だけを持たせます。複雑さはパーツを増やして出すのではなく、組み合わせで出します。
  2. 「何を」は必須、「どうやるか」は任意です。どうやるかは how と style にだけ書けます。書かなければ実行エンジンの標準の動きになり、書いたらその通りにしか作れません。
  3. 順序は書きません。並列が標準です。thing の1件は、それぞれ独立した1つのレコードです。レコードをまたぐ処理はすべて並列に、同じレコードの中の処理は1つずつ行います。順序が必要なときは、flow（状態）か relate（ルールの関係）で表します。
  4. 決めていないことはエラーになります。曖昧なまま渡すことはできません。
  5. 入れ子は禁止です。条件の中に条件を書かず、名前を付けて段階的に積み上げます。
  6. 何でも作れますが、危ないことは action の中身に閉じ込めます。外側（仕様と契約）は絞り、内側（action の中身）は契約を守れば何を書いてもかまいません。
  7. 同じ意味の語は1つだけにします。else はどこでも「逃げ道」、do はどこでも「やること」を表します。> はどこでも「ぶつかったらこちらが勝つ」、| はどこでも「どれか1つ」を表します。

5. 各パーツ

thing（データの形。旧 entity）

thing Application
  company   Company   gone[block]
  deadline  date
  owner     User      gone[remove too]
  memo      text
  status    [draft | submitted | passed | failed]
  • 1件が1つのレコードです。レコードの中の書き換えは1つずつ処理されます。
  • 項目は 名前 型 を並べて書きます。: は付けません。名前と型は色分けで見分けます。
  • 状態は 名前 [a | b] と書きます。
  • 別のレコードを指す項目には、指した先が消えたときにどうするかを gone[...] で必ず書きます（7.3）。

flow（状態の流れ）

flow Application.status
  draft -> submitted -> passed | failed
  failed > passed
  • 状態は -> の通りにしか動けません。たとえば draft から passed へは飛べません。
  • flow で管理する項目は move でしか変えられず、set は禁止です。
  • failed > passed は、同じレコードに矛盾する move が同時に来たときの勝者を表します（旧 on conflict failed wins over passed）。同時に来る可能性があるのに書いていなければ、エラーになります。
  • flow には「状態の流れ」だけを書きます。動作の順番は書きません。

list（条件で絞った集まり）

list DueSoon
  of    Application
  where status is draft
  where deadline within 3 days
  sort  deadline
  • where を複数行書くと、すべてを満たすもの（and）が対象になります。1行の中に and / or / かっこは書けません。
  • list から list を作って積み重ねられます。循環参照はエラーです。
  • for の代わりになるのが list です。ルールや通知は「当てはまるものすべて」に効きます。
  • within 3 days は暦日で数え、今から3日後の日の終わりまでを含みます。
  • sort deadline desc と書くと逆の順（新しい順）になります。書かなければ昇順です。
  • from は of に、sort by は sort に変わりました（16章）。

match（値ごとの結果）

match Application.status to color
  draft     -> red
  submitted -> gray
  passed    -> blue
  else      -> gray
  • else がないとエラーになります。ただし、宣言された状態をすべて書いた match は else を省略できます。
  • 宣言にない状態を左側に書くとエラーになります。打ち間違いを止めるためです。
  • 左側は | でまとめられます（saturday | sunday -> weekend）。
  • match の中に match は書けません（入れ子）。

rule（きっかけとやること）

rule Remind
  why   締切を落とさないため
  when  every day at 21:00
  do    notify owner each of DueSoon
  example
    given   Application
      company   "Osaka Gas"
      deadline  "9/24 23:59"
      status    draft
    at      "9/21 21:00"
    expect  notify "Osaka Gas"
  • rule は why（任意）、when、where（任意）、do、example で書きます。

when（きっかけ）

when に書けるのは出来事だけです。状態は where に書きます（when deadline within 3 days は禁止です）。

when に書ける出来事は次のものに限られます。

  • 時間: every day at 21:00 / every monday at 9:00 / at 9/24 23:00
  • 人: user says "..." / user taps X on 画面か thing
  • 書き方は決まっているものの、まだ実行エンジンが起こさない出来事もあります（check で E07 になります）。 user holds X / user swipes X left / user drags X to Y / user types in X / user opens Scene / user leaves Scene がこれにあたります。board の列の移動は 〇〇 moves to 状態 として起きます。
  • データ: 〇〇 is created / 〇〇 moves to 状態 / 〇〇 is removed
  • 外: Gmail gives new message（connect の gives）

一覧の元は ponte/forms.py にあり、python -m ponte guide --rules で表にして出せます。

{...} で取り出した値は変数になります。このとき、対象のレコードは必ず絞ります。 when user says "submitted {company}" → do move Application where company is {company} to submitted

画面で押された1件は this で指します。

where（起きる条件）

rule の where は、押された1件（this）の条件です。条件に合わないとき、その rule は静かに起きません。失敗の通知も出ず、画面のボタンも押せなくなります。

rule Borrow
  when  user taps borrow-button on Item
  where status is free
  do    create Loan
          item  this
          due   7 days from now

do（やること）

do は1つだけ書けます。2つやりたいときは rule を分けて、relate の then でつなぎます。書ける形は次の表のものだけで、ほかの書き方は check でエラー（E31）になります。

書き方すること
notify me "..."きっかけの人に通知する
notify owner each of DueSoon一覧のそれぞれのレコードの owner が指す人に通知する
move this to submitted押された1件の状態を動かす
move item of this to lentthis の item 項目が指すレコードを動かす
move Application where company is {company} to submitted絞ったレコードを動かす
remove this押された1件を消す（7.3）
go Detail / go Detail with this画面を移る
create Loan（下に字下げして「項目 値」）レコードを作る
set yen to result項目を書き換える（状態は set でなく move で変える）
FindYen / FindYen with memoaction を呼ぶ。with で、入力を this の項目から渡す
connect の does（Gmail send mail など）外に頼む

通知には宛先を書きます。宛先は me か、項目の名前（notify borrower "..."）です。通知の文に入れる {item} は、this の項目か when の {…} です。その項目が別のレコードを指す場合は、指しているレコードの名前が入ります。

値の書き方

create の「項目 値」と set の値には、次のものを書けます。

値意味
this押された1件
me今使っている人
"文字"書いた文字そのもの
7 days from now今からの期間（minutes / hours / days / weeks）。年まで入れて保存し、推測はしない
{名前}when で取り出した値
項目 of thisthis の項目の値
result直前の action の答え（set でだけ使える。std の例は 9.5）

そのほか

  • ルール同士の関係は relate に書きます。
  • flow の状態ごとにルールを書いていて抜けがあると、「passed のときは？」という警告が出ます。

relate（ルール同士の関係）

relate
  ReadMail     then    FileMail
  ManualAdd    then no FileMail
  CheckSpam    before  FileMail
  NotifyFailed >       Remind
  LineNotify   else    MailNotify

どの行も「左が先、右が後」です。

書き方意味
A then BA が終わったら B が動く
A then no BA をやったら、この後 B は動かない。B がすでに済んでいても取り消さない
A before BB が動くとき、A は済んでいる。A が終わっても B は勝手に動かない
A > B同時に当てはまったら A が勝つ
A else BA が失敗したら B をやる
  • A then B の途中で処理が落ちても、言語が裏で「このレコードで A は済んだ」ことを記録しているので、続きから再開できます。
  • action に else があり、relate でも同じ action に else を書いた場合はエラーになります。逃げ道は1つだけです。

action（中身が空の部品。契約だけを書く）

action ExtractDeadline
  in      mail text
  out     found monthday | missing
  example "10/15(木)12:00まで"            -> found 10/15 12:00
  example "【締切9/24 23:59】"            -> found 9/24 23:59
  example "来週中にご提出ください"        -> missing
  example "9/24 23:59 または 9/30 23:59"  -> missing
  never   guess the year
  else    ask user
  by      ai
  how
    limit 5 seconds
  • 旧 input / output は in / out になりました。
  • example は最低2つ必要です。中身は、すべての例を通らないと採用されません。
  • else も必須です。自信がないときの逃げ道（ask user / use default ... / skip）を書きます。
  • 契約の矛盾はエラーになります。たとえば、example の答えが out の型に合わない場合や、never と out の型がぶつかる場合です。never guess the year なのに out が年の必要な date になっているのが後者の例です。
  • 次の表の never は、中身ができたときに機械が大量の入力で確かめます。それ以外の never は、今は機械では確かめられません。ただし AI への指示にはなります。
never確かめ方
guess the year例の入力と、年のない入力をいくつか流して、答えに年（4桁の数）が出ないか
depend on width例の入力を全角にして流し、半角のときと同じ答えになるか
return empty例の入力とおかしな入力を流して、値が空の答えを返さないか
failおかしな入力（空、長すぎる、絵文字、ありえない日付など）でも止まらないか
  • 失敗や「見つからない」も、out の状態で表します（found ... | missing）。

by（誰が中身を埋めるか）

書き方いつ中身
（書かない）なしaction の中にその場で書いた do。AI も別ファイルも使わない
by aiビルドのときに1回AI が do を書いて固定する。人も読めて直せる
ask ai実行のたびに毎回AI に聞く。do はない。how に時間かお金の上限が必須
by code "extract.ponte"なし自分で書いた do
by Gmail実行のたびにconnect 先が行う

誰が埋めても、同じ example、never、else で検証されます。

do（action の中身）

  do
    text  = normalize mail
    hits  = find all Deadline in text
    kind[one | none | many] = match count of hits
                                1    -> one
                                0    -> none
                                else -> many
    found = match kind
              one  -> found monthday of first of hits
              none -> missing
              many -> missing
  • 書けるのは 名前 = 式 と、名前を付けた match だけです。
  • 答えになるのは、ほかのどの行からも使われていない行です。そのような行がちょうど1つでなければエラーになります。答えの行に [...] は必要ありません（形は out に書いてあるためです）。書く場合は answer[found monthday | missing] のように、out の形と同じにします。
  • 一時的な状態は 名前[a | b] = match ... で宣言して使います。
  • 書き換え、ループ、再帰、true/false はありません。そのため、必ず止まります。
  • 実行の順番は名前の依存関係で決まり、上から順に実行されるわけではありません。
  • 使える道具は 10章にまとめています。

shape（文字の形。正規表現の代わり）

shape Deadline
  month  digits 1..2
  "/"
  day    digits 1..2
  maybe  "(" any 1 ")"
  maybe  space
  hour   digits 1..2
  ":"
  minute digits 2

how（どうやるか。任意）

  • how は rule と action の中にだけ書けます。
  • 書かなければ AI が決めます。書いたら、AI はその通りにしか作れません。
  • 例: check every 10 minutes / limit 5 seconds / limit 1 yen / on failure retry 3 times / repeat ... until 〇〇 or 1 hour passed
  • until には回数か時間の上限が必須です。ないとエラーになります（無限ループを防ぐためです）。
  • action の limit N seconds と on failure retry N times は、動かすときに守られます。時間を過ぎたら失敗とし、失敗したら決めた回数だけやり直します。

group（まとまり）

group Mail
  rule ReadMail
    when  Gmail gives new message
    do    ExtractDeadline

  rule FileMail
    do    create Application

  relate
    ReadMail then FileMail
  • group は名前でくくるだけのもので、継承はありません。外からは Mail.ReadMail で呼びます。
  • group の中の字下げは入れ子と数えません。group の中に group は書けません。
  • 別のファイルは use "mail.ponte" で取り込みます。エラーは、取り込んだ元のファイルと行で示されます。

tbd（まだ決めていないこと。旧 unknown）

tbd
  timezone of deadline
  who can delete Application
  • tbd が残っているとビルドできません。AI は埋めずに、質問を返します。
  • ## との違いは、答えの案があるかどうかです。tbd には答えがなく、## には答えの案がすでに書いてあります。

never（やってはいけないこと）

  • never は action の中にも、ファイル全体にも書けます。
  • never は、生成されたコードのガードとテストになります。証明できる違反は、ビルド前にエラーになります。
  • action の never は、自動で作った大量の入力で検証します。たとえば年のない入力を何百個も作り、すべてが missing か else になるかを確かめます。

6. 画面

「何を見せるか」は scene、look、part、input に書き、「どう見せるか」は style に書きます。書かなかった見た目は AI が決めます。

scene（場面）

scene Home
  menu[open | closed] = closed
  top     Header
  main    match count of DueSoon
            0    -> EmptyNote
            else -> DueSoon as cards
  side    Application as list
  bottom  button add
  over    match menu
            open   -> Menu
            closed -> nothing
  • 置き場所は top / main / side / bottom / over（上に重ねる）です。細かく並べるときは row / column / grid 3 を使います。
  • 出し分けには match を使います。nothing は何も出さないことを表します。
  • 画面だけの状態は 名前[a | b] = 最初の値 と書きます。

画面の移動

flow scene
  Home -> Detail -> Edit
  Home -> AddApplication

rule OpenDetail
  when  user taps card on DueSoon
  do    go Detail with this
  • 画面は flow scene の矢印の通りにしか移動できません。矢印にない移動はエラーになります。

look（見せ方）

look DueSoon as cards
  title   company
  sub     DeadlineBadge of deadline
  mark    color of status
  button  submitted-button named 提出した

look Header
  button menu-button   named メニュー  toggle menu
  button close-button  named 閉じる    set menu closed
  • 見せ方の種類は cards / list / table / detail / input / calendar / board / chart / tabs / dialog / sheet / toast / map / media です。
  • board では、flow から状態ごとの列が自動で作られます。カードを動かすと move の出来事が起きます。
  • chart は、状態ごとの件数を棒で表します。group by 項目 で分け方を、sum 項目 で棒の高さを合計に変えられます。sum に使えるのは数の項目だけです（例: 家計メモの「費目ごとの合計」）。 `` look ByKind as chart group by kind sum yen
  • 画像を扱うには、thing の項目を photo image にして input に書きます。これで画像を選べるようになります（png / jpg / gif / webp、5MB まで）。種類は中身の先頭で確かめます。一覧では、look に image photo about name と書くと写真が出ます。about は読み上げ用の説明で、公開するときは必須です。画像は、そのレコードを who で見られる人にだけ表示されます。
  • input に状態の項目を書くと、選ぶ形になります。ただし flow のある状態は選べません（ボタンの rule で move します）。
  • **画面だけの状態は、look の中で toggle 状態 / set 状態 値 と書けます。** この場合 rule は必要ありません。データ（thing の項目）は rule の move でしか変えられません。

part（自分で作る部品）

part DeadlineBadge
  in    deadline monthday
  do
    left = days until deadline
    urgency[today | soon | later] = match left
      0    -> today
      1..3 -> soon
      else -> later
  show  text "あと{left}日"
  mark  urgency

リアルタイム

  • 何も書かなくても、画面は常に最新になります。レコードが変わると、それを表示している画面も自動で変わります。

7. データと人

7.1 who（誰が何をできるか）

who
  user   can see    Application where owner is me
  user   can change Application where owner is me
  admin  can do     everything
  nobody can remove Application
  • 書いていないことは誰もできません。
  • who が1行もない thing はエラーになります。
  • rule も who に従います。user says や user taps で動く rule は、その人ができることしかできません。
  • ログインの方法は connect に任せます。
  • 役割: user 以外の役割（admin など）は、thing User の role [member | admin] に書きます。その人の role の値が役割になります。書いていない役割を who に使うとエラー（E28）になります。
  • 役割の変更も、普通の状態と同じく flow User.role、rule、who で守ります。
  • 最初の1人は仕様から決められないため、ponte role spec.ponte taro admin で決めます。2人目からは画面で決めます。
  • where it is not me で「自分には使えない」ことを書けます。これにより、自分を管理者から外せなくなり、管理者が0人になることを防げます。
  • 動詞は see / create / move（状態を動かすだけ）/ change（作る、動かす、書き換える）/ remove です。
  • 入力を開くボタンは、その thing を作れる人にだけ表示されます。

7.2 保存

  • 保存は言語が受け持ちます。thing を書けばデータは残ります。どのデータベースを使うかは書きません。

7.3 消したときの扱い

  • ほかのレコードを指す項目には gone[...] を必ず書きます。ないとエラーになります。
  • 消すには rule の do remove this を使います。who の can remove が必要です。消すと 〇〇 is removed の出来事が起きます。
書き方意味
gone[remove too]一緒に消す
gone[leave empty]空にする
gone[block]指されている間は消せない

7.4 thing を変えたとき

change Application to v2
  add     memo text = ""
  rename  company to corp
  remove  owner
  remove  state passed -> failed
  • thing の形が前回のビルドと違うのに change がなければ、エラーになります。
  • 動かすときに、保存してある古いデータは change の通りに今の形へ移されます。足した項目の初期値、名前の変更、消した項目、消した状態の移し先が使われます。
  • 足した項目に初期値がないとエラーになります。
  • 状態を消すときは、その状態だったレコードの移し先が必須です。

8. 外とつながる（connect）

connect Gmail
  gives   new message  Message
  does    send mail    to text, body text -> sent | failed
  needs   key GMAIL_TOKEN
  limit   100 per hour
  • gives は、向こうから届く出来事です（when Gmail gives new message）。
  • does は、こちらから頼めることです。結果は必ず状態で返ります。
  • needs は秘密の値です。値そのものは仕様に書かず、実行するときに渡します。
  • limit は回数の上限です。
  • does が失敗したときの逃げ道（relate の else か、結果を match して書くもの）がないとエラーになります。
  • 言語の中は依存ゼロです。外との境界は、connect に宣言した口だけです。

9. テスト（example）

rule MarkSubmitted
  when  user says "submitted {company}"
  do    move Application where company is {company} to submitted
  example
    given   Application
      company  "Osaka Gas"
      status   draft
    given   Application
      company  "Other"
      status   draft
    says    "submitted Osaka Gas"
    expect  Application is submitted
      company  "Osaka Gas"
    expect  Application is draft
      company  "Other"
  • example は3段で書きます。given（前の状態）、出来事、expect（結果）の順です。
  • レコードの中身は字下げして1行に1つずつ書きます。 given Application の下に company "Osaka Gas" のように並べます。かっこと , は使いません。
  • given で別の thing を指す項目は、そのレコードの名前で書けます（item "カメラ"）。
  • 前の状態: given thing の名前（下に中身を書く）
  • 出来事: at "..." / says "..." / taps X on thing の名前（下に中身を書く）/ taps X on 画面の名前 / gets Gmail new message "..." / adds thing の名前（下に中身を書く。人が作ったことにし、〇〇 is created の出来事も起きる）
  • 結果: expect notify "..." / expect X is 状態 / expect 箱（下に中身を書き、その中身のレコードがあるかを確かめる）/ expect no Loan / expect 2 Loan（件数）/ expect scene Detail / expect Home shows 2 cards（存在しない scene に shows を書いたら失敗）/ expect nothing

ponte test は穴さがしもします。example がすべて通ったうえで、どの example も確かめていないところを示します（--strict を付けると失敗として扱います）。対象は次のとおりです。

  • when がある rule なのに example がなく、どの example の中でも動いていない
  • flow の矢印（a -> b）を、どの example も通っていない
  • action の out の答えの形（found / missing など）を出す example がない

11. 実行モデル

  • thing の1件（レコード）が1つのアクターです。レコードは互いに独立しています。この考え方は、Erlang や Go（goroutine と channel）と同じです。
  • ルールはすべて独立しています。並列を書かなくても並列に動きます。
  • 同じレコードへの書き換えは、届いた順に1つずつ処理します。矛盾は flow の > で決めます。
  • ルール同士の順番と強さは relate で決めます。
  • 画面はレコードの変化を受けて自動で変わります。
  • 実行には自前の実行エンジンを使い、spec を直接動かします。その後、WebAssembly に直接変換します。Go などほかの言語やライブラリには依存しません。

E01match に else がない書いていない値が来たときに、何をするかが決まっていないためです。最後に else -> 結果 を書きます。宣言した状態をすべて書いた場合、else は不要です。
E02until に上限がない終わらない可能性のある待ちは、アプリを止めてしまうためです。repeat ... until 〇〇 or 1 hour passed のように、回数か時間の上限を書きます。
E03action の example が2つ未満例が1つだけでは、中身（自分で書いても AI が書いても）が正しいかを確かめられないためです。当たる例と当たらない例（-> missing など）を、少なくとも1つずつ書きます。
E04action に else がないaction の中身が答えを出せなかったときの動きが必要なためです。else skip や else ask user のように、答えが出なかったときの動きを書きます。
E05tbd が残っている決まっていないことを残したまま動かすと、その部分を誰かが推測で決めてしまうためです。内容を決めて tbd を消します。決められない場合は、その部分を使わない形に書き換えます。
E06## が残っている## は、書いた人が確認を保留している箇所を示す印です。内容を確かめてから、## を消すか #（通常のコメント）に変えます。
E07when に状態を書いている「期限が近い」のような状態は、いつ起きるかが決まっていないためです。when には出来事（every day at 8:00 や user taps ...）を書き、状態は where か list で絞り込みます。
E08move の対象が絞り込まれていないどの1件を動かすかが決まらないまま、複数のレコードがまとめて動いてしまうためです。move this to 状態 にするか、list で1件に絞り込みます。
E10競合する move の優先順位が決まっていない同じ1件に異なる move が同時に届いたとき、どちらを優先するかが決まらないためです。flow に failed > passed のように優先順位を書きます。
E11list の参照が循環しているA の元が B で、B の元が A だと、中身が決まらないためです。どちらかを thing から直接絞り込む形に変えます。
E12入れ子入れ子は読み違えやすいため、1段で書く決まりにしています。内側の部分に名前を付けて外に出し、その名前を使います。
E13action の約束が食い違っているexample の答えや never が out の形に合っていないと、確かめることができないためです。out に書いた形（found monthday | missing など）に合わせて、example と never を書き直します。
E14relate の then / before が循環しているA の後に B、B の後に A が動くと、処理が終わらないためです。どこかの then を外すか、条件付きの rule に分けます。
E15relate の優先順位が双方向になっているA > B と B > A が両方あると、どちらも優先されないためです。どちらか一方だけを残します。
E16before の前の rule が起きないA before B と書いても A が起きる経路がなければ、B はいつまでも起きないためです。A のきっかけ（when）を書くか、before を外します。
E17失敗したときの動きが2つあるaction の else と relate の else が両方あると、どちらが動くかが決まらないためです。どちらか1つにします。
E18match に宣言されていない状態がある宣言にない状態の枝は、打ち間違いであることが多いためです。宣言にある状態名に直すか、宣言に状態を追加します。
E19who がない thing がある書いていない操作は誰にもできない決まりのため、このままでは誰も見ることができません。who に user can see Thing where ... などを書きます。
E20他のレコードを指す項目に gone がない指している先が消えたときに、こちらのレコードをどうするかが決まっていないためです。gone[remove too]、gone[leave empty]、gone[block] のいずれかを付けます。
E21thing の形を変えたのに change がない保存済みのデータを新しい形にどう合わせるかが、決まっていないためです。change Thing to v2 に、追加した項目の初期値（add memo text = ）や名前の変更を書きます。
E22ask ai に上限がないAI への問い合わせが止まらないと、費用と時間がかかり続けるためです。how に時間か費用の上限（limit 5 seconds や limit 1 yen）を書きます。
E23connect が失敗したときの動きがない外部サービスは失敗することがあり、そのときの動きが決まっていないためです。relate に rule名 else 〇〇 を書きます。
E24flow scene にない画面の移動画面の移動も flow と同じく、書いた経路しか通れないためです。flow scene に矢印を追加するか、移動先を直します。
E25words の訳が足りない一方の言語だけ文字が欠けていると、その言語の利用者に意味が伝わらないためです。words ja と words en の両方に、同じ名前で書きます。1つの言語だけのアプリでは、words を書かずに "文字" と直接書くこともできます。
E26名前のないボタンまたは説明のない画像読み上げ機能の利用者に、ボタンの役割が伝わらないためです。公開するときだけエラーになります。ボタンには named 名前 を、画像には説明を付けます。
E27通貨の異なる money の足し算円とドルをそのまま足すと、意味のない数になるためです。同じ通貨どうしで足すか、通貨ごとに分けて表示します。
E28定義されていない名前、または知らない言葉存在しない部品、list、項目、アイコンを指したり、節や操作の言葉を打ち間違えたりすると、その行は無視されます。書いたつもりの動きが起きないため、エラーにします。エラーに表示された「もしかして」の名前に直すか、定義を追加します。
E29rule に do が2つ以上ある1つの rule には1つの処理だけを書きます。2つあると、片方だけ失敗したときの結果が決まらないためです。rule を2つに分けて、relate の A then B でつなぎます。
E30通知の宛先がない誰に知らせるかが決まっていないと、通知が誰にも届かないためです。notify owner ... のように、人を指す項目か me を書きます。
E31書き方が正しくない（do、example の手順、読めない行）決まった形以外は、実行エンジンが動かせないためです。また、example の手順の打ち間違いを見逃すと、確かめていない例が通ってしまいます。do は ponte guide --rules の表にある形で書きます。example の手順は given / adds / at / says / taps / gets / expect のいずれかです。
E32型が合わない、または存在しない状態や項目存在しない状態や項目、型の違う値は、空の一覧や起きない rule になります。動かす前に見つけるため、エラーにします。エラーに表示された候補（「todo / done」など）から選んで直します。
W09（注意）flow の状態に対応する rule がない他の状態には rule があるのに、その状態のときの rule だけがありません。考慮漏れの可能性があります。その状態のときに起きることを rule に書きます。何もしない場合は、この注意は無視してかまいません。
W26（注意）名前のないボタンまたは説明のない画像試作中は注意だけを表示します。公開するとき（--publish）はエラーになります。ボタンには named 名前 を、画像には説明を付けます。

E32 の中身は下に書きます。1つずつの説明は ponte explain E32 でも見られます。

警告

  • W09（flow の状態の rule の抜け）と W26（試作中の読み上げ対応の漏れ）は警告です。
  • ponte test の穴さがし（9章）も警告です。--strict を付けると失敗になります。

E32 で確かめること

E32 では、まず rule ごとに this が何の thing かを決めます。when の on 〇〇 や 〇〇 is created から決め、relate の then の先の rule では前の rule から引き継ぎます。create の後は、作ったレコードが this になります。そのうえで、次のことを確かめます。

  • 存在しない状態への move、存在しない項目への set、where、with、通知の {…}、状態を set で書き換えること（move を使います）
  • 値の型: set yen to me（number に User）/ item me（Item に User）/ result の型（action の out から決まります）
  • this が決まらないのに this を使うこと、list の where の項目、stats の sum に数でない項目を使うこと
